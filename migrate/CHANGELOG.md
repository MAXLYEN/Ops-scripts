# 版本迭代记录

各文件独立编号。本次按现有头注释建立目录记录；旧注释未标日期的版本保持日期未记载，不补造历史。

## 2026-09-30：一键迁移演练时新机的容器也不许主动连外网

一键迁移的演练在新机上用正式恢复（`--no-cron`，不是 `--drill`）起容器，这时旧机还在服务：新机上 Xboard 的定时任务会重复给用户发提醒邮件，Komari 看到被控端全都离线（它们还在向旧机上报）会发告警，之前没有拦。演练机那套外连限制做成可单独开关，一键迁移在演练时加上、切换时撤掉、回滚时加回。回滚时加回而不是撤掉：回滚后新机回到「停着容器、带生产数据、旧机在服务」的待命状态，新机一重启，`restart: always` 的容器会被 dockerd 拉起来。

| 文件 | 原版本 → 当前版本 | 变更 |
| --- | --- | --- |
| `restore-from-backup.sh` | 1.3.1 → 1.4.0 | 新增 `--no-egress`：正式恢复也在起容器前加上与 `--drill` 相同的外连限制（加不上就不起容器），列进手动步骤；正式恢复时不记成要 `teardown` 的文件。不带 `--no-egress` 的正式恢复发现本机有这套限制时，起容器前撤掉（撤不掉告警并列出 `egress off`）。新增 `egress on\|off`：单独加上（失败返回非零）/ 撤掉；演练机上拒绝 `off`。撤的时候先按本版重写脚本再 `stop`（脚本被删过或是旧版写的也撤得掉），单元 `disable --now`；`teardown` 改用同一套 |
| `live-migrate.sh` | 1.0.0 → 1.1.0 | 演练时新机恢复带 `--no-egress`（上次恢复出来的重跑也带），停容器后限制留着；切换那次 `restore --force` 不带，由恢复脚本起容器前撤掉；回滚脚本第 1 步先在新机 `egress on` 再 `standby`，加不上照样停容器、复原本机，并提示补做。计划、回滚说明同步。「DNS 已经改好」的确认改用公共库的 `is_yes`（`lib/common.sh` 1.2.6），前后空格、大小写、全角字符不再让 yes 被当成否 |

vw 包与 xboard 包都收系统配置、全部业务库与账号、全部 compose 项目。文件和库原先就按「较新的包说了算」标成被覆盖，compose 项目和账号没有，锁版本又在去重之前做。

| 文件 | 原版本 → 当前版本 | 变更 |
| --- | --- | --- |
| `restore-from-backup.sh` | 1.3.0 → 1.3.1 | compose 项目与内容相同的一批账号也按较新的包去重；锁版本只处理每个项目、每个 compose 文件最新的那一条（原先每个项目锁两到四遍，镜像清单重复，第二遍还会报 `cp: are the same file`）；启动容器、Xboard 启动后步骤、建账号、记录 PLACED 都跳过被覆盖的条目（原先各做两遍）；被覆盖的库不再报「已恢复过，跳过」；手动步骤同样的一条只列一次；演练时本机本来就有、内容相同的 systemd 单元（面板自己的服务）不再提示，其余的提示改为「原机启用的单元，隧道这类会连到生产机」 |

## 2026-09-29：真机演练发现的三处

第一次在真机（Vultr 东京，Debian 12 + 宝塔 13.1 + MySQL 5.7.44）上做 `--drill` 演练，恢复本身 1 分 11 秒、0 告警，但有三处要人工补救。以前的测试一律带 `--no-start`，启动、重载 nginx 与 teardown 停容器这几条路径从没跑过；这次用记录调用的假 docker、假 nginx 补上。

| 文件 | 原版本 → 当前版本 | 变更 |
| --- | --- | --- |
| `restore-from-backup.sh` | 1.2.0 → 1.3.0 | 新布局把面板的整个 `vhost/` 作为一个目录放回，nginx 这一步只认单个 `vhost/nginx/*.conf` 条目，直接跳过了检查与重载，本机访问各站点全是 000；改为放下的路径与站点目录互为上下级就按本机站点目录里现有的 `*.conf` 检查引用、`nginx -t` 后重载。Komari 指标库（`METRICS_DB_NAME`）按设计不进包，它的账号却因「对恢复的库没有授权」被跳过，新机既无库也无账号，Komari 报 Access denied 起不来；改为账号照原机恢复（host 照 `DB_CLIENT_HOST`），恢复出的授权里有它、本机又没有这个库时建空库（utf8mb4，记入状态，teardown 一并删），Komari 启动时自己建表。teardown 判断 compose 文件用的 `ls compose.y*ml docker-compose.y*ml` 在只有其中一种文件名时就失败，容器一个都没停、也不告警，随后撤掉外连限制；改为任一文件名都认，`down -v --rmi all` 失败时退回只删容器，仍停不下就中止，外连限制、库和文件都不动，手动处理后可重跑 |

## 2026-09-29：演练机的容器不许主动连外网

演练机上起的 Xboard、Komari、Vaultwarden 用的是生产数据：Xboard 的定时任务会给真实用户发到期提醒邮件，Komari 看到被控端全都离线（它们还在向生产机上报）会往告警渠道发通知。

| 文件 | 原版本 → 当前版本 | 变更 |
| --- | --- | --- |
| `restore-from-backup.sh` | 1.1.0 → 1.2.0 | `--drill` 起容器前装 `/usr/local/sbin/ops-drill-egress` 与同名 systemd 单元（开机自启，排在 docker 之前），在 `DOCKER-USER` 链拒绝从容器网桥发起、去往网桥以外的新连接（IPv4 必须成功，IPv6 尽力）；回包、宿主机 nginx 反代到容器、容器连宿主机 MySQL、dockerd 拉镜像都不受影响。加不上就不起容器并告警；`--no-start` 时列进手动步骤。用 host 网络的项目告警说明拦不住。重跑不叠加规则；`teardown` 撤掉规则并删掉脚本与单元。正式恢复不加 |

## 2026-09-28：原机还在时的一键迁移

原机还活着、计划内换机器时，只有 `01`–`09` 这条多步手动流程：建立在 `03` 冷快照上（从停服那一刻起一直停着），`07` 只恢复 `CONTAINER_DATA_DIRS`、只生成启动命令，比每日包的 rootfs + 还原清单与 `restore-from-backup` 覆盖得少。决定：`01`–`09` 保留为旧流程（服务不在备份包里的机器还要用），前置机换机器改用下面的一键迁移，它调用 `08`，不调用其余几步（取舍见 README「01–09 怎么处理」）。

| 文件 | 原版本 → 当前版本 | 变更 |
| --- | --- | --- |
| `live-migrate.sh` | 新增 → 1.0.0 | 在旧机上运行。预检两台机器（密钥登录、Debian 12、init/、opsget 固定版本、docker、MySQL 大版本、nginx / 宝塔、磁盘、备份密码、新机没有别人的数据），不合要求拒绝且两台都不动；演练时旧机照常服务：备份脚本 `--local-only` 现做加密包、SSH 直传并核对 sha256，新机 `restore --no-cron` 恢复并起服务，`check` 比对、`08` 验收、经 `--resolve` 逐站对比两台、检查隧道后停掉新机容器；切换时先写回滚脚本，备份任务的 cron 行加 `#MIGRATE-PAUSED `（与 `03` 同一个标记）、停全部容器，再出包传过去，新机 `restore --force` 并启动；DNS 列出要改的记录，终端里亲手确认后经公共 DNS（DoH）复核；DNS 切换前 `rollback` 随时回到旧机，之后拒绝并说明怎么切回。SSH 放行名单：每次恢复后在新机上临时放行旧机、复核通过后删掉；落地机、LiteLLM 节点与主机清单里只放行旧前置机的机器，照旧机的规则给新机出口 IP 放行，复核通过后删掉旧机的；操作者自己的 IP 交给恢复脚本核对。known_hosts 预先记上旧机的主机密钥（恢复后新机用它） |
| `restore-from-backup.sh` | 1.0.2 → 1.1.0 | 新增 `--no-cron`：正式恢复并启动，但不装定时任务，列进手动步骤；这时结尾不再提示手动跑一次备份（会从这台机器往网盘传包）。头部说明改为原机还在时用 `live-migrate` |
